The Pythonic Way (Truthiness)
Empty data structures (like lists, dictionaries, strings, sets, and tuples) are considered "falsy" in Python, meaning they evaluate to False in a boolean context (e.g., an if statement). Non-empty structures are "truthy". 
You can leverage this behavior with the if statement or the not operator:

String	if my_string:	if not my_string:	my_string = ""
Tuple/Set	if my_tuple:	if not my_tuple:	my_tuple = ()
None	if my_var is not None:	if my_var is None:	my_var = None

Якщо я маю не індексовані зміни в локальному репо. команда git pop може їх переписати якщо на зовнішньому репо були зроблені зміни?
Ні, команда
git pull не перепише ваші локальні неіндексовані (unstaged) зміни автоматично. 
Git розроблений дуже обережно, щоб захистити вашу роботу. Якщо ви спробуєте виконати git pull (який складається з git fetch та git merge або git rebase), і виявлені зміни з віддаленого репозиторію стосуються тих самих файлів, які ви змінили локально, Git зупинить операцію і видасть повідомлення про помилку. 
Що станеться:

    Ви виконуєте git pull.
    Git завантажує зміни з віддаленого репозиторію (це частина git fetch).
    Git намагається об'єднати їх з вашою поточною локальною гілкою.
    Якщо виникає конфлікт (тобто ви змінили ті самі рядки у файлі, які були змінені і на віддаленому репо), Git припиняє операцію об'єднання і повертає робочу директорію у вихідний стан, залишаючи ваші локальні зміни недоторканими.
    Вам буде запропоновано або зафіксувати, або приховати ваші зміни перед повторною спробою. 

Єдиний виняток: Якщо віддалені зміни стосуються файлів, які ви змінили локально, але конфлікту не виникає (наприклад, зміни в різних файлах або в різних частинах одного файлу), git pull може успішно об'єднати зміни. Ваші локальні зміни залишаться у вашій робочій копії як неіндексовані після завершення об'єднання.

У ліцензії
CC0 1.0 Universal відмовляється автор (творець) твору або правовласник. 
Вони відмовляються (відмовляються або не вимагають) від усіх своїх авторських та суміжних прав на твір у всьому світі, настільки повно, наскільки це можливо згідно із законом. 
Деталі відмови:

    Хто відмовляється: Особа або організація, яка володіє авторськими правами на твір і застосовує до нього ліцензію CC0 (в юридичному тексті називається "Affirmer" або "той, хто стверджує").
    Від чого відмовляються: Від усіх майнових авторських прав та пов'язаних/суміжних прав (наприклад, прав на бази даних). Це фактично переводить твір у суспільне надбання (public domain).
    Мета: Дозволити будь-кому копіювати, змінювати, розповсюджувати, виконувати та використовувати твір для будь-яких цілей, включаючи комерційні, без необхідності запитувати дозвіл або вказувати авторство.
    Важливо: У деяких юрисдикціях певні немайнові права автора (наприклад, право на ім'я або право на цілісність твору) можуть залишатися невідчужуваними та не можуть бути повністю відкинуті, навіть за допомогою CC0. 

Отже, CC0 — це інструмент, який дозволяє творцям максимально повно відмовитися від контролю над своєю роботою, щоб сприяти її найширшому використанню.

А яка ліцензія зобов'язує використовувати код у публічній площині, зберігає право власності практично за вторцем, але суміжна з open source спільнотою при цьому запобігає патентовим посяганням, запобігає використанню у комерційній діяльності, запобігає використанню у мережевій(хмарній інфраструктурі для приватних комерційних осіб) та навчанню на нейромережах. Тобто для людського використання only.
Це дуже специфічний і суворий набір вимог.
Жодна стандартна, загальновизнана ліцензія з відкритим вихідним кодом (відповідна визначенням OSI) не може задовольнити всі ваші критерії одночасно.
Ліцензії з відкритим кодом зазвичай вимагають дозволу на комерційне використання, модифікацію та використання в мережі, щоб відповідати основним принципам відкритого програмного забезпечення.
Ви шукаєте ліцензію, яка:

    Зберігає право власності автора. (Це роблять більшість ліцензій, автор зберігає права, але видає дозвіл на використання).
    Суміжна з open source спільнотою (тут виникає конфлікт з пунктами нижче).
    Запобігає патентовим посяганням. (Деякі сильні ліцензії, як GPLv3, мають патентні положення).
    Запобігає використанню у комерційній діяльності. (Ключове обмеження, яке виключає її з категорії Open Source та Free Software).
    Запобігає використанню у мережевій/хмарній інфраструктурі для приватних комерційних осіб. (AGPLv3 намагається регулювати мережеве використання, але не забороняє комерцію).
    Запобігає навчанню на нейромережах. (Нове, специфічне обмеження, яке не є стандартним).
    Тільки для людського використання.

Рішення: нестандартні або сильно обмежені ліцензії
Вам потрібно буде використовувати одну з "Source Available" ліцензій (доступний вихідний код, але не "Open Source" за визначенням OSI), або створити власну, або об'єднати існуючі.
Найближчі варіанти, які включають деякі з ваших обмежень:
1. Ліцензії без комерційного використання (Non-Commercial - NC)
Ліцензії Creative Commons мають варіант NC (NonCommercial), наприклад:

    CC BY-NC-SA 4.0 (Із зазначенням авторства, Некомерційна, Із поширенням на тих же умовах).

Ці ліцензії не призначені для програмного забезпечення і мають юридичні проблеми при застосуванні до коду, але вони забороняють комерційне використання. Вони також не покривають питання нейромереж чи патентів специфічно для коду.
2. Сучасні "Source Available" ліцензії
Деякі сучасні компанії створюють ліцензії для запобігання використанню великими хмарними провайдерами (як Amazon, Google). Приклади:

    SSPL (Server Side Public License) від MongoDB: Вимагає, щоб будь-хто, хто надає програмне забезпечення як послугу, публікував весь свій вихідний код. Це не забороняє комерцію, але ускладнює її для хмарних провайдерів. Вона не є OSI-approved.
    BSL (Business Source License): Дозволяє використовувати код безкоштовно до певного часу або за певних умов, а потім він перетворюється на Open Source.

Резюме
Якщо вимагається заборона комерційного використання, ваш код не може бути ліцензований як стандартний "Open Source".
Вам, швидше за все, доведеться використовувати кастомну ліцензію або ліцензію Creative Commons BY-NC, адаптовану для коду, яка прямо забороняє комерцію, використання в мережевих сервісах для третіх осіб, та, можливо, додає пункт про заборону навчання ШІ на ньому.
Жодна стандартна ліцензія не містить усіх цих пунктів одночасно.
Відповіді ШІ можуть містити помилки. Щоб отримати юридичну консультацію, зверніться до спеціаліста. Докладніше

Ліцензія, яка відповідає вашим вимогам
Ліцензія, яка найкраще відповідає вашому уточненому опису — це GNU Affero General Public License, Version 3 (AGPLv3).
Вона забезпечує більшість ваших вимог, крім прямої заборони комерційного використання чи навчання ШІ (що не є стандартними положеннями в Open Source ліцензіях).
Як AGPLv3 працює:

    Для приватного (особистого) користування: Можна (без обмежень).
    Для комерційного використання: Можна, але якщо ви розповсюджуєте чи використовуєте програмне забезпечення як мережевий сервіс (хмара), ви зобов'язані надати вихідний код усім користувачам цього сервісу за умовами AGPLv3.
    Зберігає право власності: Так, автор зберігає права, але ліцензія надає дозволи та накладає зобов'язання.
    Запобігає патентовим посяганням: Так, AGPLv3 містить потужні положення про надання патентних прав від учасників, які використовують код.
    Код суміжного має бути відкритий: Так, це ключова вимога (Copyleft/Share-alike).

AGPLv3 не забороняє комерційну діяльність і не забороняє навчання нейромереж. Ліцензії Open Source не можуть містити таких заборон.

GNU General Public License (GPL) версії 3 (GPLv3).
Це найпопулярніша ліцензія, яка відповідає всім уточненим критеріям:

    Зберігає право власності автора: Так, ви залишаєтеся правовласником, але надаєте ліцензію на використання.

    Для комерційного використання - тільки якщо код суміжного буде також відкритий: Так. Це ключова умова Copyleft. Будь-хто, хто розповсюджує модифіковану версію вашого коду (комерційно чи ні), зобов'язаний надати вихідний код своїх модифікацій під тією ж ліцензією GPLv3.

Висновок
GPLv3 — це, ймовірно, саме те, що вам потрібно для забезпечення "людського використання only" у сенсі збереження відкритості екосистеми коду. Вона гарантує, що ніхто не зможе взяти ваш код, закрити його, модифікувати та продавати як пропрієтарний продукт.
Якщо ви хочете, щоб навіть використання вашого коду на приватному сервері (хмарному сервісі SaaS), до якого користувачі отримують доступ через мережу, вимагало публікації вихідного коду, тоді оберіть AGPLv3 (Affero General Public License v3).
А в "Affero General Public License v3" треба щось дописувати в тіло ліцензії?
Ні, в
Affero General Public License v3 (AGPLv3) не потрібно нічого "дописувати" в саме тіло ліцензії.
Текст ліцензії є стандартизованим юридичним документом, який не можна змінювати.
Що потрібно зробити, щоб застосувати AGPLv3:

    Додати стандартний заголовок (boilerplate notice): Ви повинні додати спеціальний текстовий блок на початку кожного вихідного файлу вашого програмного забезпечення. Цей блок вказує, що файл розповсюджується на умовах AGPLv3, і містить посилання на повний текст ліцензії.
    Включити повний текст ліцензії: Ви повинні включити повну копію ліцензії AGPLv3 (зазвичай у файлі з назвою LICENSE або COPYING) до вашого проєкту.

Чомусь під час git pull вилізло:

Merge branch 'dev' of https://github.com/author/repo-name into dev
# Please enter a commit message to explain why this merge is necessary,
# especially if it merges an updated upstream into a topic branch.
#
# Lines starting with '#' will be ignored, and an empty message aborts
# the commit.
Це повідомлення означає, що команда
git pull, яку ви запустили, не змогла виконати "fast-forward" оновлення і автоматично ініціювала злиття (merge) гілок.
Git відкрив ваш текстовий редактор за замовчуванням, щоб ви могли написати повідомлення комміту злиття.
Чому це сталося?

    У вашій локальній гілці dev були локальні комміти, яких ще не було у віддаленій гілці origin/dev.
    І у віддаленій гілці origin/dev були нові комміти, яких не було у вашій локальній гілці.

Ваші гілки розійшлися, і Git не може просто додати нові зміни зверху ваших (що називається "fast-forward"). Замість цього він створює спеціальний "merge commit" (комміт злиття), який фіксує об'єднання двох різних історій гілок.
Що робити далі?
Git чекає від вас підтвердження цього злиття. Вам потрібно зберегти файл і закрити редактор:

    Прийміть повідомлення за замовчуванням: Git вже згенерував стандартне повідомлення: Merge branch 'dev' of .... Зазвичай цього достатньо.
    Збережіть файл:
        Якщо ви використовуєте nano (часто стандартний редактор): натисніть Ctrl + O (зберегти), потім Enter (підтвердити ім'я файлу).
        Якщо ви використовуєте vim (інший поширений редактор): натисніть :wq (write and quit) і потім Enter.
    Закрийте редактор:
        Для nano: Ctrl + X.
        Для vim: Після :wq він закриється автоматично.

Після того, як ви закриєте редактор, Git завершить операцію pull, створить комміт злиття, і ваш локальний репозиторій буде оновлено.

Добре, що потрібно для перетворення свого застосунку на пакет?
Щоб перетворити свій застосунок на пакет Python (який можна встановити через
pip та імпортувати в інші проєкти), вам потрібно виконати кілька ключових кроків:
1. Організація структури проєкту
Переконайтеся, що ваш код має чітку структуру.

your_project_name/
├── your_package_name/
│   ├── __init__.py  # Обов'язковий файл, який робить папку пакетом
│   ├── main.py      # Ваш основний код програми
│   ├── module_a.py  # Інші ваші модулі
│   └── ...
├── LICENSE          # Файл ліцензії (AGPLv3)
├── README.md        # Опис проєкту
└── setup.py         # АБО pyproject.toml і setup.cfg (файли з налаштуваннями пакета)

2. Створення файлів конфігурації пакета
Вам потрібен один із двох варіантів (новіший pyproject.toml або старий setup.py):
Варіант A: Використання pyproject.toml та setup.cfg (рекомендовано)
Це сучасний стандарт.
setup.cfg:
ini

[metadata]
name = your-package-name
version = 0.1.0
author = Your Name
author_email = your.email@example.com
description = A simple interactive tool for iteratively navigating website files.
long_description = file: README.md
long_description_content_type = text/markdown
url = github.com
license = AGPLv3
classifiers =
    Programming Language :: Python :: 3
    License :: OSI Approved :: GNU Affero General Public License v3
    Operating System :: OS Independent

[options]
packages = find:
python_requires = >=3.8
install_requires =
    requests>=2.25.1
    # Додайте інші залежності тут

[options.packages.find]
where = .

[options.entry_points]
# Це дозволяє запускати вашу програму з командного рядка як 'your-package-name'
console_scripts =
    your-package-name = your_package_name.main:main

Будьте обачні, використовуючи код.
pyproject.toml:
Цей файл вказує Python, який інструмент використовувати для збірки (наприклад, setuptools):
toml

[build-system]
requires = ["setuptools>=61.0"]
build-backend = "setuptools.build_meta"

Будьте обачні, використовуючи код.
Варіант B: Використання лише setup.py (старіший метод)
python

from setuptools import setup, find_packages

setup(
    name="your-package-name",
    version="0.1.0",
    author="Your Name",
    author_email="your.email@example.com",
    description="A simple interactive tool...",
    long_description=open('README.md').read(),
    long_description_content_type="text/markdown",
    url="github.com",
    packages=find_packages(),
    classifiers=[
        "Programming Language :: Python :: 3",
        "License :: OSI Approved :: GNU Affero General Public License v3",
        "Operating System :: OS Independent",
    ],
    python_requires='>=3.8',
    install_requires=[
        "requests>=2.25.1",
        # інші залежності
    ],
    entry_points={
        'console_scripts': [
            'your-package-name = your_package_name.main:main',
        ],
    },
)

Будьте обачні, використовуючи код.

    main()

Триває обробка
Сенс робити застосунок пакетом (навіть якщо у нього прості функції)
безумовно є, але це залежить від ваших цілей:
Коли має сенс робити пакет:

    Повторне використання коду (Reusability):
    Якщо ви плануєте використовувати цю "просту" логіку в інших своїх майбутніх проєктах, перетворення її на пакет дозволить вам просто встановити її через pip install your-package-name замість того, щоб копіювати файли вручну.
    Зручність розповсюдження та встановлення:
    Якщо ви хочете поділитися цим інструментом з іншими людьми (колегами, друзями) або опублікувати його на PyPI, пакет — це стандартний і найпростіший спосіб встановлення для кінцевого користувача. Вони просто вводять pip install your-package-name, і все готово, включаючи всі залежності (наприклад, requests).
    Керування залежностями:
    Пакет чітко визначає, які зовнішні бібліотеки йому потрібні (requests>=2.25.1), що спрощує підтримку проєкту і запобігає проблемам "на моїй машині працює".
    Створення виконуваної команди (Entry Point):
    Як ми налаштували в setup.cfg (console_scripts), пакет дозволяє запускати вашу програму з будь-якого місця в терміналі простою командою (наприклад, my-super-tool), а не командою python main.py з конкретної папки.
    Професійний вигляд:
    Навіть простий інструмент, оформлений як пакет, виглядає більш завершеним та професійним.

Коли сенсу менше:

    Ви єдиний користувач, і код ніколи не покине ваш комп'ютер:
    Якщо ви використовуєте скрипт лише для власних потреб, і він завжди запускається в одній і тій самій папці, то оформлення його як пакета може бути зайвим.

Резюме:
Для "простої інтерактивної тулзи", яку ви описували, сенс є. Це перетворює ваш скрипт із простого набору файлів на повноцінний, легко встановлюваний інструмент, що значно покращує досвід використання як для вас, так і для інших.

Так а я можу присвоїти своєму застосунку AGPLv3 ліцензію якщо він використовує пакет(типу curl_cffi) під  MIT License?
Тут хіба немає протиріч? Або може я мушу щось зробити?
Ні, протиріч тут
немає, і ви можете присвоїти своєму застосунку ліцензію AGPLv3, навіть якщо він використовує бібліотеки (наприклад, curl_cffi) під ліцензією MIT.
Насправді, це дуже поширена та повністю сумісна комбінація ліцензій.
Чому це працює (Сумісність ліцензій):

    MIT License — це "дозвільна" (permissive) ліцензія. Вона дуже ліберальна і, по суті, каже: "Робіть із цим кодом усе, що завгодно, включаючи використання в пропрієтарних (закритих) або Copyleft проєктах, тільки збережіть наше повідомлення про авторські права".
    AGPLv3 (та інші Copyleft ліцензії) є "обмежувальними" в тому сенсі, що вони вимагають відкритості похідних робіт.

Ліцензія MIT дозволяє вам взяти код і включити його в проєкт із сильнішими вимогами. Ви просто дотримуєтеся умов MIT (зберігаєте повідомлення про авторські права) і застосовуєте умови AGPLv3 до свого коду, який використовує цей MIT-код.
Що вам потрібно зробити:
Єдина вимога — це дотримання умов ліцензії MIT, яка вимагає збереження оригінального повідомлення про авторські права та тексту ліцензії.

    У вашому проєкті (у файлі LICENSE AGPLv3 та заголовках файлів) ви заявляєте, що ваш власний код є AGPLv3.
    Ви маєте визнати використання curl_cffi під MIT:
        У вашому файлі README.md або NOTICE (якщо ви його створите) варто згадати, що ваш проєкт використовує бібліотеку curl_cffi, яка ліцензована під MIT.
        Найкраще мати копію ліцензії MIT для curl_cffi десь у вашому репозиторії (наприклад, у your_project/vendor/curl_cffi_LICENSE.txt), щоб виконати умову "зберегти повідомлення про авторські права".

Отже, ви не мусите нічого змінювати в тілі AGPLv3; просто переконайтеся, що ви визнаєте використання MIT-ліцензованого коду.

Вони лише вимагають включення їхніх оригінальних повідомлень про авторські права, що зазвичай автоматично виконується завдяки наявності їхніх ліцензійних файлів у встановлених пакетах.

Триває обробка
Абсолютно вірно! Ви правильно розумієте ситуацію.
Ви ліцензуєте конкретно свій код. Ви не ліцензуєте код залежностей.
Ваш код, який використовує виклики до інших пакетів (таких як requests, colorama, curl_cffi), є вашою інтелектуальною власністю, і ви можете застосувати до нього AGPLv3.
Основні моменти:

    Ви не включаєте їхній код фізично у свій репозиторій (ви не копіюєте вихідні файли pyperclip.py у свою папку проєкту).
    Ви лише декларуєте залежність у файлах конфігурації (setup.cfg або requirements.txt).
    Користувачі встановлюють залежності окремо через pip, і при цьому вони автоматично погоджуються з умовами ліцензій (MIT, BSD) цих пакетів.

Ваша AGPLv3 розповсюджується лише на ті файли, які ви створили і до яких додали свій заголовок ліцензії.
Отже, немає потреби додавати повні тексти ліцензій MIT/BSD до вашого проєкту або виконувати складні дії, окрім як просто перерахувати ці залежності у вашому файлі setup.cfg (як ми робили раніше).
